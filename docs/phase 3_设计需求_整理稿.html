Phase 3需求

1. Phase 3目标

本阶段不再只停留在“角色能动、能打”的演示层，而是要把角色状态机、动画切分、音效触发和 DE1-SoC 集成接口一次性定义清楚，保证游戏逻辑同学、动画切分同学、渲染/硬件同学可以并行开发。

设计原则： 顶层游戏状态尽量少，角色状态尽量稳定，动画选择只消费状态机输出，不直接依赖按键输入。这样后续接键盘、手柄、脚本回放时都不用改动画层。

2. 游戏层状态机

从实现和协作角度，不建议把“P1 胜 / P2 胜 / Time Out / 平局”拆成 4 个平级 GameState。更稳妥的方案是：

  • game_state 只保留 MENU / PLAYING / GAME_OVER 三个大状态
  • winner 表示 NONE / P1 / P2 / DRAW
  • finish_reason 表示 KO / TIME_OUT / DOUBLE_KO / EXIT

这样 UI、音效和结束动画都只需要监听 GAME_OVER，再根据 winner 和 finish_reason 选择文案、音效和演出。

状态 进入条件 退出条件 画面/音效要求
MENU 启动游戏或对局中按 L 返回主菜单 任意玩家按任意有效输入后进入 PLAYING 菜单两帧或多帧循环；菜单 BGM 循环；确认时播放短确认音效
PLAYING 菜单确认开始，重置血量、位置、朝向、计时器 任一玩家 HP 归零、双方同时归零、计时结束、或按 L 正常战斗演出；角色状态机、碰撞、血条、倒计时全部在此状态更新
GAME_OVER PLAYING 中触发 KO / TIME_OUT / DOUBLE_KO 结算动画播完后，按 J/K 重开，按 L 回菜单 根据 winner + finish_reason 显示 “P1 WIN / P2 WIN / DRAW / TIME OUT”；播放结束音效

2.1 顶层完整流转

BOOT / RESET
  -> MENU

MENU
  -- 任意玩家任意有效输入 -->
  ROUND_INIT（重置血量 / 位置 / 朝向 / 倒计时 / 清空角色状态）
  -> PLAYING

PLAYING
  -- P1 HP = 0, P2 HP > 0 --> GAME_OVER[winner = P2, finish_reason = KO]
  -- P2 HP = 0, P1 HP > 0 --> GAME_OVER[winner = P1, finish_reason = KO]
  -- P1 HP = 0, P2 HP = 0 --> GAME_OVER[winner = DRAW, finish_reason = DOUBLE_KO]
  -- timer = 0 --> GAME_OVER[winner = compare_hp, finish_reason = TIME_OUT]
  -- 任意玩家按 L --> MENU

GAME_OVER
  -- 结算动画播完 且 按 J / K -->
  ROUND_INIT -> PLAYING
  -- 结算动画播完 且 按 L --> MENU

其中 ROUND_INIT 更适合作为状态进入动作，而不是常驻状态。这样顶层枚举仍然能保持 MENU / PLAYING / GAME_OVER 三态，但逻辑流程已经完整。

2.2 顶层状态判定顺序

为了避免一帧内同时满足多个结束条件时出现不一致，顶层游戏状态每帧建议按以下顺序判定：

  1. 先处理主动退出：任一玩家按 L，立即回 MENU
  2. 再处理角色死亡：优先判断是否双死，再判断单方 KO
  3. 最后处理倒计时结束：若双方都未死但计时归零，按剩余 HP 判定胜者
  4. 只有以上都未触发时，才保持 PLAYING

这条顺序尤其重要，因为它决定了“双死”和“Time Out”不会互相覆盖，也不会出现本地渲染和 FPGA 渲染显示不同结算结果。

3. 角色状态机拆分

角色层建议采用“一个主可视状态 + 一个攻击子类型 + 一个结束原因”的方式，而不是把所有动作都堆成独立枚举。这样既能和当前代码里的 fighter_visual_state_t、fighter_attack_command_t 对齐，也方便动画同学按层切分素材。

3.1 完整角色状态树

CHARACTER
  ├─ ALIVE
  │   ├─ GROUND
  │   │   ├─ IDLE
  │   │   ├─ WALK
  │   │   ├─ CROUCH_ENTER -> CROUCH_HOLD -> CROUCH_EXIT
  │   │   ├─ GUARD
  │   │   ├─ ATTACK_GROUND
  │   │   │   ├─ NORMAL: STARTUP -> ACTIVE -> HIT_CONFIRM / BLOCK_CONFIRM / RECOVERY
  │   │   │   ├─ FIREBALL: STARTUP -> ACTIVE -> HIT_CONFIRM / BLOCK_CONFIRM / RECOVERY
  │   │   │   ├─ DRAGON_PUNCH: STARTUP -> ACTIVE -> HIT_CONFIRM / BLOCK_CONFIRM / RECOVERY
  │   │   │   └─ SWEEP: STARTUP -> ACTIVE -> HIT_CONFIRM / BLOCK_CONFIRM / RECOVERY
  │   │   └─ HIT_GROUND
  │   │   └─ BLOCK_STUN
  │   └─ AIR
  │       ├─ JUMP_START -> JUMP_RISE -> JUMP_FALL -> LAND
  │       ├─ ATTACK_AIR
  │       │   ├─ JUMP_ATTACK: STARTUP -> ACTIVE -> HIT_CONFIRM / RECOVERY
  │       │   ├─ FORWARD_JUMP_ATTACK: STARTUP -> ACTIVE -> HIT_CONFIRM / RECOVERY
  │       │   └─ BACK_JUMP_ATTACK: STARTUP -> ACTIVE -> HIT_CONFIRM / RECOVERY
  │       └─ HIT_AIR
  └─ DEAD
      └─ KO_ENTER -> KO_DOWN

上面这棵树是“完整状态机”，但实现时不建议直接变成一个超大的平级枚举。更推荐的落地方式是：

  • visual_state 负责主可视层：IDLE / WALK / JUMP / CROUCH / GUARD / ATTACK / HIT / KO
  • attack_command 负责攻击子类型：普通、发波、升龙、跳攻、扫腿
  • state_frame 负责状态内部第几帧
  • airborne / grounded、landing_event、event_flags 负责补足空中和落地细节

这样逻辑层仍然清楚，动画层也能拿到完整信息，不需要做二次推断。

3.2 统一中断优先级与锁定规则

优先级 事件 强制切换 说明
1 HP 归零 KO 最高优先级，立刻打断所有动作和输入缓冲
2 被命中且未成功格挡 HIT_GROUND 或 HIT_AIR 打断普通移动和攻击；若是格挡成功则转 block 事件而非普通受击
3 防御成功并吃到攻击 BLOCK_STUN 必须区别于单纯按住防御的 GUARD，因为它有硬直、音效和闪白反馈
4 空中落地 LAND 空中攻击和空中受击都要先进入落地段，再回地面状态
5 攻击输入成立且攻击冷却为 0 ATTACK 攻击进入后先走 Startup，再到 Active；若命中或被防住则插入命中确认或格挡确认
6 跳跃输入成立且角色在地面 JUMP_START 跳跃只允许从地面中立类状态进入
7 防御键按住 GUARD 仅限地面；空中默认不进入地面防御状态
8 下蹲键按住 CROUCH 仅限地面；和防御同时存在时优先防御
9 左右移动输入成立 WALK 左右同时按下时建议视为无效移动，回中立
10 无有效输入 IDLE 最低优先级默认状态

锁定规则建议如下：

  • Startup 和 Active 期间不允许切到普通移动状态，但允许被 HIT 或 KO 打断
  • 攻击命中后，攻击方进入一个很短的 HIT_CONFIRM 窗口，再进恢复；这个窗口可用于命中特效、顿帧和音效同步
  • 攻击被格挡后，攻击方进入 BLOCK_CONFIRM 或更长恢复；防御方进入 BLOCK_STUN
  • Recovery 期间可以记录输入缓冲，但默认不立即切状态，等恢复结束再结算
  • HIT 期间忽略除死亡之外的所有玩家输入
  • BLOCK_STUN 期间忽略移动和攻击输入，只允许在硬直结束后回到 GUARD 或中立
  • KO 期间忽略全部玩家输入，直到 round reset
  • 空中状态不允许切入地面 CROUCH 和地面 GUARD

3.3 可视状态优先级

为避免同一帧出现多个状态竞争，角色可视状态优先级统一如下：

KO > HIT_STUN > BLOCK_STUN > ATTACK > JUMP > GUARD > CROUCH > WALK > IDLE

动画、音效、特效都以这条优先级为准。比如角色在空中被打中，应先播放 HIT；角色成功防住攻击时应优先显示 BLOCK_STUN 而不是继续摆普通防御姿势；角色 HP 归零时直接切 KO。

3.4 角色核心状态表

状态 进入条件 主要动画要求 音效建议 退出条件
IDLE 地面无输入、未受击、未攻击、未防御 循环待机动画，建议 4-6 帧，带轻微呼吸感 无强制音效 收到左右/跳跃/下蹲/防御/攻击输入，或进入受击、死亡
WALK 地面按住 A 或 D 循环步行动画，建议 6-8 帧；允许根据 facing 镜像 可选脚步音，原型阶段可不做 方向释放后回 IDLE；跳跃/攻击/防御/受击/死亡时中断
JUMP 地面按下 W；或处于空中物理阶段 至少拆成 起跳 / 空中滞空 / 下落 / 落地 4 段；动画同学可以合并到一个 clip，但要保留落地事件点 起跳音、落地音可选；至少保留落地事件 落地后根据输入转到 IDLE / WALK / CROUCH / GUARD；空中按攻击可转攻击子状态
CROUCH 地面按住 S 建议拆成 蹲下 / 蹲住 / 起身 3 段，最低可先做 蹲住 1 个循环帧 无强制音效 松开 S 回地面状态；攻击则进入扫腿；受击/死亡优先
GUARD 地面按住 K 防御架势需明显收缩轮廓，保证和待机区分；受击时可额外叠加 block flash 格挡音效应独立于受击音效 松开 K 后回地面状态；若成功防住攻击则进入 BLOCK_STUN 而非普通 HIT
BLOCK_STUN 角色处于 GUARD 且碰撞系统返回 BLOCKED 短时后仰或收缩受力动作，建议 2-4 帧；要明显区别于站立防御 格挡音 + 盾闪/白闪 硬直结束后，若 K 仍按住则回 GUARD，否则回中立地面状态
ATTACK 按下 J 或组合键且攻击冷却为 0 统一走攻击主状态，但必须再区分 attack_command 和 attack_phase 选择具体 clip 挥击声、发波声、升龙声、命中声按子状态触发 攻击恢复结束后回到对应地面/空中状态；命中后插入 HIT_CONFIRM，被防住后插入 BLOCK_CONFIRM；受击/死亡可打断
ATTACK_HIT_CONFIRM 攻击 Active 帧命中对手，且对手未成功格挡 本质上仍属于攻击动作，但建议有短暂停顿、打击闪光或攻击者姿态定格 命中音、命中特效、命中顿帧 短窗口结束后进入攻击恢复段；若对手 HP 归零则允许直接衔接 KO 演出
ATTACK_BLOCK_CONFIRM 攻击 Active 帧命中对手，但对手成功格挡 攻击者出现被挡住的停顿或回弹感，时长通常短于普通恢复但长于命中确认 格挡音、挡火花、轻微顿帧 短窗口结束后进入恢复段，通常不能立即连招
HIT 被命中且 HP > 0 建议至少做 1 套通用受击动画，若资源够可拆成站立受击/下段受击/空中受击 命中音效，必要时叠加轻微受击闪白 受击硬直结束后回到合法状态；若 HP 归零立刻转 KO
KO HP 归零 建议拆成 倒地启动 + 倒地停留；不得循环回普通待机 KO 音效、胜负播报 仅在 round reset 后离开该状态

3.5 攻击子状态与切分规范

当前输入方案已经确定如下：

  • J：普通攻击
  • A + J：发波
  • D + J：升龙
  • W + J：跳跃攻击
  • W + D + J：前跳攻击
  • W + A + J：后跳攻击
  • S + J：扫腿

策划和动画协作上，建议每个攻击 clip 都至少标出 Startup / Active / Recovery 三段。原型阶段即使判定逻辑先简化成“攻击按下即命中检测”，动画资源也应该按这三段切，避免以后返工。

现在补充要求：每种攻击都要定义“命中后”和“被格挡后”的反馈窗口。即使它们最终不单独存成 sprite 文件，也要在 metadata 里标出 hit_confirm_frame 和 block_confirm_frame。

攻击类型 输入 建议动画 clip 建议相位切分 关键事件点 音效建议
FIGHTER_ATTACK_NORMAL J atk_normal Startup 3f / Active 2f / Recovery 5f 第 4 帧出拳命中；第 4 帧触发挥击音；命中后插入 2f HIT_CONFIRM；被挡时插入 2f BLOCK_CONFIRM 轻挥击 + 命中音
FIGHTER_ATTACK_FIREBALL A + J atk_fireball Startup 5f / Active 1f / Recovery 8f Active 首帧生成飞行物或发波特效；命中或格挡时由投射物事件回写攻击结果 蓄力/发射音 + 命中音
FIGHTER_ATTACK_DRAGON_PUNCH D + J atk_dragon_punch Startup 4f / Active 4f / Recovery 10f 第 3-4 帧身体上冲；命中特效偏强；若被格挡，恢复惩罚应比普通攻击更重 重挥击音 + 命中音
FIGHTER_ATTACK_JUMP_ATTACK W + J atk_jump_neutral Startup 2f / Active 3f / 空中恢复到落地 落地后强制回 JUMP 的落地段 空挥音 + 命中音
FIGHTER_ATTACK_FORWARD_JUMP_ATTACK W + D + J atk_jump_forward Startup 2f / Active 3f / 空中恢复到落地 需要更明显前冲姿态 空挥音 + 命中音
FIGHTER_ATTACK_BACK_JUMP_ATTACK W + A + J atk_jump_back Startup 2f / Active 2f / 空中恢复到落地 重心后仰，和前跳攻击区分 空挥音 + 命中音
FIGHTER_ATTACK_SWEEP S + J atk_sweep Startup 4f / Active 3f / Recovery 9f 命中判定点在低位；建议对方可用低位受击或倒地；被格挡时进入低位格挡反馈 下段挥击音 + 命中音

3.7 给碰撞/攻击判定同学的接口约定

碰撞体积与攻击判定模块不应该直接修改动画，而是每帧向状态机返回一次战斗结算结果。建议接口最少包含：

typedef enum {
  FIGHTER_CONTACT_NONE = 0,
  FIGHTER_CONTACT_HIT,
  FIGHTER_CONTACT_BLOCKED,
  FIGHTER_CONTACT_TRADE,
  FIGHTER_CONTACT_WHIFF
} fighter_contact_result_t;

状态机收到判定结果后的约定动作如下：

判定结果 攻击方状态 防守方状态 附带动作
NONE 保持原攻击相位 保持原状态 无
HIT ATTACK_HIT_CONFIRM HIT_GROUND / HIT_AIR 或 KO 扣血、播命中音、发命中特效、设置 hitstop
BLOCKED ATTACK_BLOCK_CONFIRM BLOCK_STUN 减伤、播格挡音、发挡火花、设置短 hitstop
TRADE 双方都进 HIT 或 KO 双方都进 HIT 或 KO 双方结算伤害，优先判断双死
WHIFF 进入普通 ATTACK_RECOVERY 保持原状态 不播命中/格挡反馈

4. 音效设计与触发条件

音效不应该散落在动画层单独判断，而是由状态机在关键事件点统一派发。原型阶段建议按优先级实现：

优先级 事件 触发条件 备注
P0 菜单 BGM 进入 MENU 时启动循环，离开时停止 当前仓库已有 Title.wav
P0 菜单确认 从 MENU 进入 PLAYING 时播放一次 当前仓库已有 Credit.wav
P0 Game Over 进入 GAME_OVER 时播放一次 当前仓库已有 Game Over.wav
P1 普通挥击 ATTACK 子状态进入 Active 帧 轻攻击通用
P1 发波发射 FIREBALL 生成投射物帧 要和普通挥击区分
P1 升龙重击 DRAGON_PUNCH Active 首帧 应体现爆发力
P1 命中 对手进入 HIT，攻击方进入 ATTACK_HIT_CONFIRM 可按轻/重攻击拆两类
P1 格挡 对手按住 K 且成功减伤，进入 BLOCK_STUN 不要和受击音共用
P1 命中确认顿帧 攻击方进入 ATTACK_HIT_CONFIRM 可不单独播音，但建议触发短 hitstop 和强特效
P2 起跳/落地 进入起跳帧、落地事件帧 用于增强重量感

5. 给动画切分同学的资源交付规范

动画同学不应该自己猜状态机逻辑。状态机负责人需要暴露稳定的 clip 名和事件点，动画同学只负责把素材切成规范资源并回填 metadata。

5.1 最低必做 clip 清单

  • idle
  • walk
  • jump_start、jump_air、jump_land
  • crouch
  • guard
  • block_stun
  • atk_normal
  • atk_fireball
  • atk_dragon_punch
  • atk_jump_neutral、atk_jump_forward、atk_jump_back
  • atk_sweep
  • hit
  • ko

5.2 命名与 metadata 建议

建议每个角色都交一份简单的 json/csv 清单，字段固定如下：

character_id, clip_id, loop, frame_count, pivot_x, pivot_y,
startup_frame, active_frame_start, active_frame_end,
sfx_frame, effect_frame, land_frame, hit_confirm_frame, block_confirm_frame, notes

例如：

ken, atk_fireball, false, 14, 24, 88, 1, 6, 6, 6, 6, -1, 7, 7, spawn projectile

这里的关键点是：动画同学只标“哪一帧出效果”，真正的碰撞和伤害仍由状态机决定。

6. 在 DE1-SoC 中如何暴露状态机给动画/渲染方

原则： HPS 侧状态机是唯一真源，动画模块只读状态快照，不直接读原始按键。这样 FPGA 渲染、framebuffer 渲染和后续录屏工具都能共用同一套输出。

6.1 软件层建议暴露的动画快照

typedef enum {
  FIGHTER_ANIM_PHASE_NONE = 0,
  FIGHTER_ANIM_PHASE_STARTUP = 1,
  FIGHTER_ANIM_PHASE_ACTIVE = 2,
  FIGHTER_ANIM_PHASE_HIT_CONFIRM = 3,
  FIGHTER_ANIM_PHASE_BLOCK_CONFIRM = 4,
  FIGHTER_ANIM_PHASE_RECOVERY = 5
} fighter_anim_phase_t;

typedef enum {
  FIGHTER_COMBAT_RESULT_NONE = 0,
  FIGHTER_COMBAT_RESULT_HIT = 1,
  FIGHTER_COMBAT_RESULT_BLOCKED = 2,
  FIGHTER_COMBAT_RESULT_TRADE = 3,
  FIGHTER_COMBAT_RESULT_WHIFF = 4
} fighter_combat_result_t;

typedef struct {
  fighter_visual_state_t visual_state;
  fighter_attack_command_t attack_command;
  fighter_anim_phase_t anim_phase;
  fighter_combat_result_t combat_result;
  uint16_t state_frame;
  uint8_t facing;
  uint8_t event_flags;
} fighter_anim_snapshot_t;

其中：

  • visual_state 决定大类动作，例如待机、行走、跳跃、受击
  • attack_command 只在 visual_state == ATTACK 时用于选 clip
  • anim_phase 让动画和音效知道现在处于 Startup / Active / HitConfirm / BlockConfirm / Recovery
  • combat_result 记录这次攻击结算结果，方便攻击方和防守方播放不同反馈
  • state_frame 表示进入当前状态后的第几帧，动画同学可据此对齐帧切换
  • facing 决定左右镜像
  • event_flags 用于一次性事件，例如 HIT、BLOCK、LAND、PROJECTILE_SPAWN

6.2 MMIO/寄存器扩展建议

当前仓库已经有：

  • PLAYER1_STATE / PLAYER2_STATE：可视状态
  • PLAYER1_FACING / PLAYER2_FACING：朝向
  • DEBUG_FLAGS：目前可用来临时打包最后一次攻击类型

为了让动画方真正可用，Phase 3 建议新增以下只读寄存器：

偏移 寄存器 作用
0x38 PLAYER1_ATTACK_CMD 当前攻击子类型，非攻击时为 0
0x3C PLAYER2_ATTACK_CMD 当前攻击子类型，非攻击时为 0
0x40 PLAYER1_STATE_FRAME 进入当前状态后的帧计数
0x44 PLAYER2_STATE_FRAME 进入当前状态后的帧计数
0x48 PLAYER1_EVENT_FLAGS 一次性事件位，例如命中、格挡、落地、发波
0x4C PLAYER2_EVENT_FLAGS 一次性事件位，例如命中、格挡、落地、发波
0x50 PLAYER1_COMBAT_RESULT 本帧攻击/受击结算结果，例如 HIT / BLOCKED / WHIFF / TRADE
0x54 PLAYER2_COMBAT_RESULT 本帧攻击/受击结算结果，例如 HIT / BLOCKED / WHIFF / TRADE

如果寄存器预算紧张，也可以把上述字段压成一个 anim_state_word，但文档和代码中都必须先固定 bit layout，避免动画同学和逻辑同学各自理解不同。

6.3 协作边界

  • 状态机负责人负责：枚举、状态优先级、命中规则、音效事件、状态快照输出
  • 动画切分负责人负责：sprite 切分、clip 命名、metadata 标注、命中确认/格挡确认帧、镜像规则、锚点统一
  • 碰撞/攻击判定负责人负责：hurtbox / hitbox / blockbox 判定，以及向状态机回传 contact_result
  • 渲染/硬件负责人负责：根据快照选 clip、推进帧、显示角色与特效，不重写游戏规则

7. Phase 3落地建议

  1. 先按当前代码中的 visual_state 和 attack_command 固定枚举值，不要频繁改名。
  2. 在状态机里补 finish_reason、state_frame、event_flags 三类字段，优先保证协作接口稳定。
  3. 动画资源先做“一套角色完整跑通”，确认命名和 metadata 规范后再批量切第二个角色。
  4. 音效先做 P0，再补攻击/格挡/命中细节，避免音频成为阻塞项。

以上方案既能和当前仓库里的 fighter_game、fighter_input、fighter_mmio 保持一致，也足够支撑 Phase 3 的动画切分与 SoC 集成工作。
