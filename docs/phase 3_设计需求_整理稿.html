Phase 3需求

1. Phase 3目标

本阶段不再只停留在“角色能动、能打”的演示层，而是要把角色状态机、动画切分、音效触发和 DE1-SoC 集成接口一次性定义清楚，保证游戏逻辑同学、动画切分同学、渲染/硬件同学可以并行开发。

设计原则： 顶层游戏状态尽量少，角色状态尽量稳定，动画选择只消费状态机输出，不直接依赖按键输入。这样后续接键盘、手柄、脚本回放时都不用改动画层。

2. 游戏层状态机

从实现和协作角度，不建议把“P1 胜 / P2 胜 / Time Out / 平局”拆成 4 个平级 GameState。更稳妥的方案是：

  • game_state 只保留 MENU / PLAYING / GAME_OVER 三个大状态
  • winner 表示 NONE / P1 / P2 / DRAW
  • finish_reason 表示 KO / TIME_OUT / DOUBLE_KO / EXIT

这样 UI、音效和结束动画都只需要监听 GAME_OVER，再根据 winner 和 finish_reason 选择文案、音效和演出。

状态 进入条件 退出条件 画面/音效要求
MENU 启动游戏或对局中按 L 返回主菜单 任意玩家按任意有效输入后进入 PLAYING 菜单两帧或多帧循环；菜单 BGM 循环；确认时播放短确认音效
PLAYING 菜单确认开始，重置血量、位置、朝向、计时器 任一玩家 HP 归零、双方同时归零、计时结束、或按 L 正常战斗演出；角色状态机、碰撞、血条、倒计时全部在此状态更新
GAME_OVER PLAYING 中触发 KO / TIME_OUT / DOUBLE_KO 结算动画播完后，按 J/K 重开，按 L 回菜单 根据 winner + finish_reason 显示 “P1 WIN / P2 WIN / DRAW / TIME OUT”；播放结束音效

3. 角色状态机拆分

角色层建议采用“一个主可视状态 + 一个攻击子类型 + 一个结束原因”的方式，而不是把所有动作都堆成独立枚举。这样既能和当前代码里的 fighter_visual_state_t、fighter_attack_command_t 对齐，也方便动画同学按层切分素材。

3.1 可视状态优先级

为避免同一帧出现多个状态竞争，角色可视状态优先级统一如下：

KO > HIT > ATTACK > JUMP > GUARD > CROUCH > WALK > IDLE

动画、音效、特效都以这条优先级为准。比如角色在空中被打中，应先播放 HIT；角色 HP 归零时直接切 KO，不再停留在普通受击。

3.2 角色核心状态表

状态 进入条件 主要动画要求 音效建议 退出条件
IDLE 地面无输入、未受击、未攻击、未防御 循环待机动画，建议 4-6 帧，带轻微呼吸感 无强制音效 收到左右/跳跃/下蹲/防御/攻击输入，或进入受击、死亡
WALK 地面按住 A 或 D 循环步行动画，建议 6-8 帧；允许根据 facing 镜像 可选脚步音，原型阶段可不做 方向释放后回 IDLE；跳跃/攻击/防御/受击/死亡时中断
JUMP 地面按下 W；或处于空中物理阶段 至少拆成 起跳 / 空中滞空 / 下落 / 落地 4 段；动画同学可以合并到一个 clip，但要保留落地事件点 起跳音、落地音可选；至少保留落地事件 落地后根据输入转到 IDLE / WALK / CROUCH / GUARD；空中按攻击可转攻击子状态
CROUCH 地面按住 S 建议拆成 蹲下 / 蹲住 / 起身 3 段，最低可先做 蹲住 1 个循环帧 无强制音效 松开 S 回地面状态；攻击则进入扫腿；受击/死亡优先
GUARD 地面按住 K 防御架势需明显收缩轮廓，保证和待机区分；受击时可额外叠加 block flash 格挡音效应独立于受击音效 松开 K 后回地面状态；被打中保持格挡判定但不切普通 HIT
ATTACK 按下 J 或组合键且攻击冷却为 0 统一走攻击主状态，但必须再区分 attack_command 选择具体 clip 挥击声、发波声、升龙声、命中声按子状态触发 攻击恢复结束后回到对应地面/空中状态；受击/死亡可打断
HIT 被命中且 HP > 0 建议至少做 1 套通用受击动画，若资源够可拆成站立受击/下段受击/空中受击 命中音效，必要时叠加轻微受击闪白 受击硬直结束后回到合法状态；若 HP 归零立刻转 KO
KO HP 归零 建议拆成 倒地启动 + 倒地停留；不得循环回普通待机 KO 音效、胜负播报 仅在 round reset 后离开该状态

3.3 攻击子状态与切分规范

当前输入方案已经确定如下：

  • J：普通攻击
  • A + J：发波
  • D + J：升龙
  • W + J：跳跃攻击
  • W + D + J：前跳攻击
  • W + A + J：后跳攻击
  • S + J：扫腿

策划和动画协作上，建议每个攻击 clip 都至少标出 Startup / Active / Recovery 三段。原型阶段即使判定逻辑先简化成“攻击按下即命中检测”，动画资源也应该按这三段切，避免以后返工。

攻击类型 输入 建议动画 clip 建议相位切分 关键事件点 音效建议
FIGHTER_ATTACK_NORMAL J atk_normal Startup 3f / Active 2f / Recovery 5f 第 4 帧出拳命中；第 4 帧触发挥击音 轻挥击 + 命中音
FIGHTER_ATTACK_FIREBALL A + J atk_fireball Startup 5f / Active 1f / Recovery 8f Active 首帧生成飞行物或发波特效 蓄力/发射音 + 命中音
FIGHTER_ATTACK_DRAGON_PUNCH D + J atk_dragon_punch Startup 4f / Active 4f / Recovery 10f 第 3-4 帧身体上冲；命中特效偏强 重挥击音 + 命中音
FIGHTER_ATTACK_JUMP_ATTACK W + J atk_jump_neutral Startup 2f / Active 3f / 空中恢复到落地 落地后强制回 JUMP 的落地段 空挥音 + 命中音
FIGHTER_ATTACK_FORWARD_JUMP_ATTACK W + D + J atk_jump_forward Startup 2f / Active 3f / 空中恢复到落地 需要更明显前冲姿态 空挥音 + 命中音
FIGHTER_ATTACK_BACK_JUMP_ATTACK W + A + J atk_jump_back Startup 2f / Active 2f / 空中恢复到落地 重心后仰，和前跳攻击区分 空挥音 + 命中音
FIGHTER_ATTACK_SWEEP S + J atk_sweep Startup 4f / Active 3f / Recovery 9f 命中判定点在低位；建议对方可用低位受击或倒地 下段挥击音 + 命中音

4. 音效设计与触发条件

音效不应该散落在动画层单独判断，而是由状态机在关键事件点统一派发。原型阶段建议按优先级实现：

优先级 事件 触发条件 备注
P0 菜单 BGM 进入 MENU 时启动循环，离开时停止 当前仓库已有 Title.wav
P0 菜单确认 从 MENU 进入 PLAYING 时播放一次 当前仓库已有 Credit.wav
P0 Game Over 进入 GAME_OVER 时播放一次 当前仓库已有 Game Over.wav
P1 普通挥击 ATTACK 子状态进入 Active 帧 轻攻击通用
P1 发波发射 FIREBALL 生成投射物帧 要和普通挥击区分
P1 升龙重击 DRAGON_PUNCH Active 首帧 应体现爆发力
P1 命中 对手进入 HIT 可按轻/重攻击拆两类
P1 格挡 对手按住 K 且成功减伤 不要和受击音共用
P2 起跳/落地 进入起跳帧、落地事件帧 用于增强重量感

5. 给动画切分同学的资源交付规范

动画同学不应该自己猜状态机逻辑。状态机负责人需要暴露稳定的 clip 名和事件点，动画同学只负责把素材切成规范资源并回填 metadata。

5.1 最低必做 clip 清单

  • idle
  • walk
  • jump_start、jump_air、jump_land
  • crouch
  • guard
  • atk_normal
  • atk_fireball
  • atk_dragon_punch
  • atk_jump_neutral、atk_jump_forward、atk_jump_back
  • atk_sweep
  • hit
  • ko

5.2 命名与 metadata 建议

建议每个角色都交一份简单的 json/csv 清单，字段固定如下：

character_id, clip_id, loop, frame_count, pivot_x, pivot_y,
startup_frame, active_frame_start, active_frame_end,
sfx_frame, effect_frame, land_frame, notes

例如：

ken, atk_fireball, false, 14, 24, 88, 1, 6, 6, 6, 6, -1, spawn projectile

这里的关键点是：动画同学只标“哪一帧出效果”，真正的碰撞和伤害仍由状态机决定。

6. 在 DE1-SoC 中如何暴露状态机给动画/渲染方

原则： HPS 侧状态机是唯一真源，动画模块只读状态快照，不直接读原始按键。这样 FPGA 渲染、framebuffer 渲染和后续录屏工具都能共用同一套输出。

6.1 软件层建议暴露的动画快照

typedef enum {
  FIGHTER_ANIM_PHASE_NONE = 0,
  FIGHTER_ANIM_PHASE_STARTUP = 1,
  FIGHTER_ANIM_PHASE_ACTIVE = 2,
  FIGHTER_ANIM_PHASE_RECOVERY = 3
} fighter_anim_phase_t;

typedef struct {
  fighter_visual_state_t visual_state;
  fighter_attack_command_t attack_command;
  fighter_anim_phase_t anim_phase;
  uint16_t state_frame;
  uint8_t facing;
  uint8_t event_flags;
} fighter_anim_snapshot_t;

其中：

  • visual_state 决定大类动作，例如待机、行走、跳跃、受击
  • attack_command 只在 visual_state == ATTACK 时用于选 clip
  • anim_phase 让动画和音效知道现在处于 Startup / Active / Recovery
  • state_frame 表示进入当前状态后的第几帧，动画同学可据此对齐帧切换
  • facing 决定左右镜像
  • event_flags 用于一次性事件，例如 HIT、BLOCK、LAND、PROJECTILE_SPAWN

6.2 MMIO/寄存器扩展建议

当前仓库已经有：

  • PLAYER1_STATE / PLAYER2_STATE：可视状态
  • PLAYER1_FACING / PLAYER2_FACING：朝向
  • DEBUG_FLAGS：目前可用来临时打包最后一次攻击类型

为了让动画方真正可用，Phase 3 建议新增以下只读寄存器：

偏移 寄存器 作用
0x38 PLAYER1_ATTACK_CMD 当前攻击子类型，非攻击时为 0
0x3C PLAYER2_ATTACK_CMD 当前攻击子类型，非攻击时为 0
0x40 PLAYER1_STATE_FRAME 进入当前状态后的帧计数
0x44 PLAYER2_STATE_FRAME 进入当前状态后的帧计数
0x48 PLAYER1_EVENT_FLAGS 一次性事件位，例如命中、格挡、落地、发波
0x4C PLAYER2_EVENT_FLAGS 一次性事件位，例如命中、格挡、落地、发波

如果寄存器预算紧张，也可以把上述字段压成一个 anim_state_word，但文档和代码中都必须先固定 bit layout，避免动画同学和逻辑同学各自理解不同。

6.3 协作边界

  • 状态机负责人负责：枚举、状态优先级、命中规则、音效事件、状态快照输出
  • 动画切分负责人负责：sprite 切分、clip 命名、metadata 标注、镜像规则、锚点统一
  • 渲染/硬件负责人负责：根据快照选 clip、推进帧、显示角色与特效，不重写游戏规则

7. Phase 3落地建议

  1. 先按当前代码中的 visual_state 和 attack_command 固定枚举值，不要频繁改名。
  2. 在状态机里补 finish_reason、state_frame、event_flags 三类字段，优先保证协作接口稳定。
  3. 动画资源先做“一套角色完整跑通”，确认命名和 metadata 规范后再批量切第二个角色。
  4. 音效先做 P0，再补攻击/格挡/命中细节，避免音频成为阻塞项。

以上方案既能和当前仓库里的 fighter_game、fighter_input、fighter_mmio 保持一致，也足够支撑 Phase 3 的动画切分与 SoC 集成工作。
